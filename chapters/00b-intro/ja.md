# ブラウザとWeb（Browsers and the Web）

> 出典: https://browser.engineering/intro.html
> 取得日: 2026-11-14
> 原文: *Web Browser Engineering*（Pavel Panchekha、Chris Harrelson 著）イントロダクションの日本語訳（学習用）

私は（ここで話しているのはクリスです）、大人になってからずっとWeb[^1]とともに生きてきました。私にとってWebは、いわば技術上の相棒のようなもので、学業でも仕事でも、Webから遠く離れたことはありません。皆さんもそうかもしれません。そしてWebを使うということは、ブラウザ（browser）を使うということです。この本を読み進めるうちに、私と同じようにWebブラウザを好きになってもらえたらと思います。

## ブラウザと私（The Browser and Me）

1990年代初めにWebとその前身[^2]に初めて出会って以来、私はブラウザとネットワーク化されたユーザーインターフェースという概念に魅了されてきました。最初期の形のWebであっても、[サーフィン](https://www.pcmag.com/encyclopedia/term/web-surfing)していると、コンピューティングの未来を目にしている気がしました。ある意味で、Webと私はともに成長してきました。たとえば、Webが商用化された1994年は、私が大学に入った年でした。大学ではかなりの時間をWebサーフィンに費やし、1999年に卒業するころには、ブラウザは有名なドットコム投機のゴールドラッシュに火をつけていました。それだけではありません。私が今働いているGoogleという会社は、Webの申し子であり、その時期に創業されました。

大学1年のとき、RedHatの営業担当者のプレゼンテーションに出席しました。当然ながらプレゼンはRedHat Linuxを売り込むためのもので、おそらく「未来のオペレーティングシステム」と呼び、「Linuxデスクトップの年」を語っていたと思います。ところが、RedHatが直面している課題を尋ねられると、その担当者が挙げたのはLinuxではなく*Web*でした。誰かが「Linux向けの良いブラウザを作る必要がある」と言ったのです。[^3]Webの最初の数年の時点で、すでにブラウザはあらゆるコンピューターに必須の構成要素でした。彼は、こんな挑戦まで投げかけました。「より良いブラウザを作るのが、どれだけ難しいというのか？」実際、どれだけ難しいのでしょうか。何がそんなに難しいのでしょうか。この問いは、長いあいだ私の心に残り続けました。[^4]

本当に、どれだけ難しいことか。Chromeの現場で11年間働いた今の私は、彼の問いへの答えを知っています。ブラウザを作ることは、簡単でもあり、途方もなく難しくもあり、意図的でもあり、偶然でもあります。そして、どこを見ても、Webの進化と歴史がひとつのコードベースに包み込まれているのが見えます。それは楽しく、尽きることのない面白さがあります。

こうして私はWebブラウザに恋をしました。今度は、皆さんもそうなる理由をお話ししましょう。

## Webの歴史（The Web in History）

Webは、壮大で突飛な実験です。今では、Webで動画を見たり、ニュースを読んだり、友人とつながったりするのが当たり前になっています。そのせいで、Webは単純で自明なもの、完成済みで、すでに作り終えられたものに見えるかもしれません。しかしWebは単純でも自明でもなく（そして確実に完成してもいません）、人々がどうすればつながり、互いに学び合えるかについての、コンピューティングのほぼ初期にまでさかのぼる[^5]実験と研究の成果なのです。

初期のインターネットは、おもに大学、研究所、大企業にあるコンピューターを物理的なケーブルで結び、アプリケーション固有のプロトコルで通信する世界規模のネットワークでした。（ごく）初期のWebは、おおむねこの土台の上に築かれました。Webページは、特定のコンピューターに保存された特定の形式のファイルでした。Webページのアドレスはコンピューターとファイルを指定し、初期のサーバーはディスクからファイルを読み出すこと以外ほとんど何もしませんでした。Webの論理的な構造は、その物理的な構造を映していたのです。

その後、多くが変わりました。Webページ用のハイパーテキストマークアップ言語（HyperText Markup Language、HTML）は、今ではたいてい、その場で動的に組み立てられ[^6]、要求に応じてブラウザに送られます。組み立てられる部品自体も動的な内容、つまりあなたの好みに合わせて調整されたニュース、受信トレイの中身、広告で満たされています。アドレスさえ、もはや特定のコンピューターを指していません。コンテンツ配信ネットワーク（CDN）が、リクエストを世界中の何千台ものコンピューターのどれかに振り分けます。より高い視点で見ると、ほとんどのWebページは、誰かの自宅のコンピューター[^7]ではなく、大企業のソーシャルメディアプラットフォームやクラウドコンピューティングサービスから配信されています。

これだけ変わっても、変わらないものがあります。Webの本質である、中核的な構成要素です。

- Webは、*ハイパーリンク*（hyperlink）で結ばれた*情報のネットワーク*である。

- ユーザーは、*ブラウザ*と呼ばれる*ユーザーエージェント*（user agent）を使ってWebをたどる。

- 情報は*ハイパーテキスト転送プロトコル（HyperText Transfer Protocol、HTTP）*で要求され、*HTML文書形式*で構造化される。

- 文書は、その内容*ではなく*、Uniform Resource Locator（URL）で識別され、動的に生成されることもある。

- Webページは、画像、動画、カスケーディングスタイルシート（Cascading Style Sheets、CSS）、JavaScriptなど、さまざまな形式の補助的なアセットへリンクできる。

- これらの構成要素はすべて、オープンで標準化されており、自由に使え、再利用できる。

哲学的な問題として、これらの原則のどれかは二次的なものかもしれません。Webのネットワーク面とレンダリング面を区別しようとすることもできるでしょう。リンクとネットワークを、特定のプロトコルやデータ形式の選択から切り離して抽象化することもできるでしょう。ブラウザは理論上必要なのかと問うこともできますし、HTTP、URL、ハイパーリンクだけが本当に不可欠なWebの要素だと論じることもできます。

そうかもしれません。[^8]Webは、結局のところ実験であり、中核となる技術は進化し、成長します。しかしWebは偶然の産物ではありません。その原初の設計は、コンピューティングについてだけでなく、人間がどのようにつながり、やり取りできるかについての真理を反映しています。Webがホスティングとコンテンツの仮想化の時代を生き延びただけでなく、栄えたのは、まさにこの原初の設計の優雅さと有効性のおかげです。

理解しておくべき重要な点は、この壮大な実験がまだ終わっていないということです。Webの本質は残り続けますが、Webブラウザを作ることで、皆さんにはその未来を形作る機会があります。

## 実際のブラウザのコードベース（Real Browser Codebases）

では、ブラウザに貢献するとはどんなことか、お話ししましょう。Chromeで働き始めて最初の数か月のあるとき、私は [`<br>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/br) タグを実装しているコードに出くわしました。あの昔ながらの `<br>` タグです。Webページに改行を入れるために何度も使ってきたものです。その実装は、Chromeでも、この本の単純なブラウザでも、ほとんどコードがないに等しいことがわかりました。

しかし、Chrome全体は、その機能、速度、セキュリティ、信頼性を含めて、*すごい*のひとことです。*何千*人年もの労力が注ぎ込まれています。Web上の何千もの企業、何百万もの開発者[^9]、何十億ものユーザーのために、もっと多くのこと、つまり機能の追加、性能の向上、「Webエコシステム」への追随を求める圧力が、絶えずかかっています。

そのようなコードベースで働くことは、気が遠くなるように感じられることがあります。会ったこともない誰かが15年前に最後に触ったコード行を、よく目にします。今でも、存在すら知らなかったファイルやクラスを見つけることがあります。不要に見えるのに、実は重要だとわかるコード行もあります。この15年前のコードは何をしているのか。私にとって初見のこれらのファイルの目的は何か。あのコードには理由があってそこにあるのか。

どのブラウザにも、数千もの未修正のバグがあります。ごく小さなミスから、無数の取り違えや不整合までさまざまです。どのブラウザも、最後のわずかな性能を絞り出すために、絶えずチューニングと最適化が必要です。どのブラウザも、複雑さを減らすために、しばしば慎重な[^10]モジュール化と抽象化の導入を通じて、コードを継続的にリファクタリングする地道な作業を必要とします。

ブラウザが、ほとんどの巨大なコードベースと違うのは、その*切迫性*です。ブラウザは、どんな「レガシー」なコードベースにも劣らず古いものですが、レガシーでは*ありません*。放棄されたり、半ば非推奨になったり、置き換えが予定されたりしているわけではありません。それどころか、世界の経済にとって不可欠です。そのためブラウザエンジニアは、捨てて置き換えるのではなく、直して改善しなければなりません。さらに、Web自体の性格が高度に分散的であるため、ブラウザが満たすユースケースは、かなりの部分で、特定のブラウザを「所有」または「支配」している企業によって*決められてはいません*。皆さんを含む他の人々が、アイデア、提案、実装を寄せることができますし、実際に寄せています。

驚くべきことに、規模もペースも複雑さもこれほどであるにもかかわらず、貢献できる余地はまだ十分にあります。今日のブラウザはすべてオープンソースで、その実装はWeb開発者のコミュニティ全体に開かれています。ブラウザは、新しいアイデアが絶えず提案され、試される巨大な研究プロジェクトのように進化します。予想どおり、失敗する機能もあれば、成功する機能もあります。成功したものは仕様に取り込まれ、他のブラウザにも実装されます。どのWebブラウザも、バグ修正でも、新機能の提案でも、有望な最適化の実装でも、貢献を受け入れています。

そして、貢献する価値があります。Webブラウザの開発は、とても楽しいからです。

## ブラウザのコードの概念（Browser Code Concepts）

HTMLとCSSは、ブラックボックス、つまり宣言的なアプリケーションプログラミングインターフェース（API）であることが意図されています。そこでは*何を*達成するかを指定し、*どうやって*達成するかを考えるのは*ブラウザ自身*の責任です。Web開発者は、自分のWebページのピクセルを自分で描くことはしませんし、たいていはできません。

そのおかげで、ブラウザは、正しく動いているかどうかに応じて、魔法のようにも、もどかしくも感じられます。しかしそれは同時に、ブラウザを、独特の課題、興味深いアルゴリズム、巧妙な最適化を備えた、かなり変わったソフトウェアにしています。ブラウザは、純粋な楽しみのために学ぶ価値があります。

これらすべてを成り立たせているのが、Webブラウザによる、[制御の反転](https://en.wikipedia.org/wiki/Inversion_of_control)、[制約プログラミング](https://en.wikipedia.org/wiki/Constraint_programming)、[宣言的プログラミング](https://en.wikipedia.org/wiki/Declarative_programming)の実装です。Webは*制御を反転*させます。仲介者であるブラウザがレンダリングの大半を担い、Web開発者はこの仲介者にレンダリングのパラメータとコンテンツを指定します。[^11]さらに、これらのパラメータは、たいてい値を直接指定するのではなく、画面上の要素の相対的な大きさや位置の間の*制約*という形を取ります。[^12]ブラウザはその制約を解いて値を求めます。同じ考え方は動作にも当てはまります。Webページは、動作が*いつ*起こるかを指定せずに、動作が起こる*こと*だけをおおむね要求します。この*宣言的*なスタイルは、開発者の視点では変更が「すぐに適用される」ことを意味しますが、内部的には、ブラウザは[怠惰](https://en.wikipedia.org/wiki/Lazy_evaluation)に振る舞い、その変更が外部から見えるようになるまで適用を遅らせられます。外部から見えるようになるのは、後続のAPI呼び出しがあるとき、またはページをユーザーに表示しなければならないときです。[^13]

ブラウザが変わった設計になっているのには、実用的な理由があります。確かに、開発者はある程度の制御と主体性を失います。ピクセルが間違っていても、開発者はそれを直接直せません。[^14]しかしその代わりに、細部を気にせずにWeb上にコンテンツを展開でき、そのコンテンツを存在するほぼすべてのコンピューティングデバイスですぐに利用可能にでき、ソフトウェアに避けられない陳腐化をおおむね避けて将来にわたってアクセス可能に保てます。

私にとってブラウザは、アルゴリズムが*生き生きと動き出す*場所です。ブラウザには、どんなコンピューターゲームよりも複雑で強力なレンダリングエンジン、完全なネットワークスタック、巧妙なデータ構造と並列プログラミング技術、仮想マシン、インタープリター言語、ジャストインタイムコンパイラ、世界最高水準のセキュリティサンドボックス、そして独特に動的なデータ保存の仕組みが含まれています。

そして実のところ、皆さんは常にブラウザを使っています。この本を読むのにも使っているかもしれません。だからこそ、ブラウザのアルゴリズムは、ほかのどこよりも親しみやすいのです。Webはすでに馴染み深いものだからです。

## ブラウザの役割（The Role of the Browser）

Webは、現代のコンピューティングの中心にあります。毎年、Webは、私たちがコンピューターでやることの、より多くの領域へと広がっています。今ではWebは、文書ベースの情報共有という本来の用途をはるかに超えています。多くの人が、ほかのアプリケーションを一切使わず、一日中ブラウザの中で過ごしています。さらに、デスクトップアプリケーションも、今では*Webアプリ*（web app）として作られ、配信されることがよくあります。Webアプリとは、ブラウザで読み込まれ、インストール済みのアプリケーションのように使われるWebページです。[^15]モバイルデバイスでさえ、アプリがアプリケーションのユーザーインターフェース（UI）の一部を描画するためにブラウザを組み込んでいることがよくあります。[^16]将来は、デスクトップもモバイルも、おおむねWebアプリのコンテナになるかもしれません。ブラウザはすでに、コンピューティングにとって重要で不可欠な存在です。

この中心性を考えると、Webがどのように動くかを知る価値があります。とりわけ、ユーザーエージェント[^17]であり、Webにおけるやり取りの仲介者であるブラウザに注目する価値があります。Webの原則を現実のものにするのは、最終的にはそこだからです。ブラウザはまた、Webの*実装者*でもあります。そのサンドボックスはWebの閲覧を安全に保ち、そのアルゴリズムは宣言的な文書モデルを実装し、そのUIはリンクをたどります。Webページが速く読み込まれ、滑らかに反応するのは、ブラウザが極めて効率的なときだけです。

## ブラウザとあなた（Browsers and You）

この本は、単純なブラウザの作り方を説明します。単純でありながら、見栄えのするWebページを表示でき、多くの興味深い挙動をサポートできるブラウザです。これから見るように、驚くほど簡単で、現実のブラウザを理解するのに必要な中核的な概念をすべて示してくれます。ブラウザは、コードになると、謎ではなくなります。

意図しているのは、前半の章を進めながら、皆さん自身のブラウザを作ってもらうことです。動き出したら、性能を改善したり機能を追加したりする機会は無限にあり、その一部は演習として提案されています。これらの演習の多くは、実際のブラウザに実装されている機能なので、ぜひ試してみてください。機能の追加は、ブラウザ開発の最も楽しい部分のひとつです。

その後、本は、私のChromeでの経験に基づいて、現実のブラウザのレンダリングエンジンのアーキテクチャに肉付けする、細部や発展的な機能へと進みます。読み終えるころには、Chromium、Gecko、WebKitのソースコードに分け入って、それほど苦労せずに理解できるようになっているはずです。

この本を通じて、ブラウザの奥深さ、複雑さ、力強さを味わってもらえたらと思います。ブラウザの美しさ、つまり巧妙なアルゴリズムとデータ構造、コンピューティングの文化や歴史との共進化、私たちの世界における中心性を伝えられたらと思います。けれども何より、この本を通じて、未来のブラウザを作っている自分自身の姿を思い描いてもらえたらと願っています。
